Part 1 · The pipelineI got every data source flowing, end to end

The project runs on three live data sources, and I built and verified the full path for each one (this is deliverable D1, now done):

  • Sensors. I wrote the InfluxDB ingestion for all 9 devices — 1,036,276 rows back to January — and the processing that regularizes readings onto an hourly grid, flags gaps instead of filling them (so a dead sensor can't fake a signal), and builds lag/rolling features. Along the way I found and fixed two bugs that only showed on live data: timezone-mismatched joins and InfluxDB returning numbers as strings.
  • Weather. I wrote the Open-Meteo client for daily temperature, rain, and ET₀ at the vineyard's exact coordinates — both the historical archive and the forecast API — plus growing-degree-day accumulation, joined onto the sensor grid.
  • Drone imagery. The hard one. The file host was down for two weeks (I root-caused it to an announced platform storage upgrade rather than waiting blind), and the imagery catalog's download links turned out to be stale — so I wrote a WebDAV client that indexes the share directly and treats it as the source of truth. Payoff: I found the stitched NDVI/NDRE orthomosaics and all 39 vineyard-block polygons already sitting on the share — things we assumed we'd have to build. I then wrote the geo layer: KMZ parsing, sensor→block spatial join (all 47 sensors mapped), and windowed zonal stats that can handle the 46 GB rasters without loading them.

Part 2 · The modelsI benchmarked 7 model families — and caught my own results lying twice

The D2 question: will soil moisture drop below the irrigation threshold in the next 6–48 hours? Before touching models, I built the testing machinery (deliverable D5): walk-forward evaluation — train strictly on the past, test on the next ~17-day fold, five folds (Figure 2) — with every model scored as skill = 1 − MAE(model)/MAE(persistence), where persistence means "predict the latest reading." Positive skill = better than doing nothing. That's the standard setup for time series (Tashman 2000).

Then I climbed the ladder: climatology, seasonal-naive, persistence, a dry-down slope rule, ridge regression (three variants), ARIMA, random forest, gradient-boosted trees. I gave the weather-aware models a deliberately generous deal — the actual future weather, as if forecasts were perfect. The work I'm most proud of this period isn't a model, it's what happened next:

  • I caught ARIMA leaking. It showed +8% skill, but the gain grew with horizon in a suspicious way. Digging in: for the first h−1 rows of each fold, the fitted Kalman filter had already seen observations past those rows' cutoff. My unit tests had missed it because they all tested horizon 1, where the leak is empty. I fixed the filter logic and wrote a regression test that plants absurd values in the leaky region and asserts forecasts can't see them.
  • I caught ridge's "+15%" being one lucky week. Fold by fold, the skill was +0.55, −1.58, −1.63, +0.01, −0.18 — the whole win was a single April rain episode (Figure 3). I added per-fold skill columns to every results table so this class of artifact can't hide again.
  • I re-tested the survivor before believing it. Post-fix, ARIMA was still +2–3% on one sensor, so I ran it on the other three. It lost 6–18% on one of them (Figure 4) — not shippable. The tree models were even less stable: big wins in scattered cells, worst-fold disasters, and at 48 h the GBT would miss a third of the irrigation alerts the naive forecast catches.

Part 3 · The productI shipped the irrigation alert

The vineyard's question is binary: will this block need water in the next h hours? Given the benchmark, the right answer is the simple one, and I made it official (ADR-0003): forecast = the latest reading, alert when it's below the threshold. On the sensors whose holdout actually crosses the threshold, that alert scores 0.95–0.99 precision and recall at every horizon. Zero parameters, nothing to retrain, easy to explain to an operator. Its one structural weakness, stated honestly: after rain, the alert takes h hours to clear. This is what the D6 API will serve to the dashboard and digital-twin teams.
